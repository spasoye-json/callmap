# A Go interface that only a library type implements gives a library call

Sometimes no type in scope implements an interface of the repo. A call through that interface is a library call when a loaded library type implements the interface. The owner decided this on 2026-10-26, after the measurement on gitea. The owner made decisions 4 and 5 on 2026-10-27, after the second code review of spec 74. The code review of spec 74 also found places where the Go extractor did not follow the spec. This record holds the decisions, the rules of the match that it needs, and the rules that follow the spec text.

This changes in part decision 2 of ADR-0024. That decision made every such call an open end with `no-implementation`.

## Decisions

1. **A repo interface that only a library type implements gives a library call.** A loaded library type is a type of a loaded package, or of a package that it imports. Its file is not in scope. A type in scope that takes the called method from a library type that it embeds counts too. An interface that no loaded type implements stays `no-implementation`. So does an interface whose only implementation takes the called method from an interface that it embeds. The extractor does not know the code that runs.
2. **A method matches by the types of its parameters and results, not by their names.** So `Read(p []byte) (int, error)` implements `io.Reader`, whose results have names. The test variant of a package and its plain variant declare 2 copies of each type. So the match compares a named type by its package path and its name.
3. **A generic type is in a group when one type argument for each of its type parameters makes its methods implement the interface.** `go/types` checks an instantiated type, but the extractor has no type arguments to try. So each type parameter of the receiver takes the type that it first meets in a method, and must match that type in the other methods. `Box[T]` with `Put(T)` and `Get() T` implements `Store { Put(int); Get() int }`, and `Label[T]` with `Put(T)` and `Get() string` does not. The extractor does not check the constraints of the type parameters.
4. **A module that the root `go.work` does not use loads on its own.** The extractor loads it with `GOWORK=off`, from its own folder, so each Go file in scope enters the document. The modules on the use lines still load once, as the workspace.
5. **A one-of group holds only the methods that a file in scope declares.** A type in scope can take the called method from a library type that it embeds. That method is a library method, so the type stays out of the group. An example is `buf struct{ *strings.Builder }` for `WriteString`.

## Rules that follow the spec text

- **The interface of the receiver decides.** A call `r.Read()` on a repo interface `RC { io.Reader; Done() }` is a one-of group over the types in scope that implement `RC`, although `io.Reader` declares `Read`. Only a call on a library interface is a library call. An interface with no name belongs to the repo when a file in scope declares one of its methods.
- **A callee with an invalid type is `missing-module` only when code that does not load gave it that type.** That code is an import that does not resolve, or a name that no loaded file declares. A missing mock is an example. The extractor follows a variable back to the expression that gave it its type. It does the same for a field, a parameter, a function result and the name of a type switch. It follows both sides of an operator such as `+`. So `charge()` with the parameter `charge gen.Charge` gives `missing-module`. A callee or a receiver whose type a local type error lost gives `untyped`. An example is `total := 1 + "cents"`.
- **Only a field, a variable, a parameter or a call result is a function value.** A type parameter is a function value when each term of its constraint has the same function type. An example is `attempt` in `func Retry[F ~func()](attempt F)`. `m["k"]()` is none of them, so it gives `other`. A slice element, such as `callbacks[0]()`, and a pointer that the call dereferences, such as `(*fn)()`, give `other` too.
- **A file that imports `C` enters the document when cgo is on, as the go tool builds it.** The go tool turns cgo off with no C compiler on the `PATH`, or with `CGO_ENABLED=0`. Then the go tool does not build the file, and it stays out of the document. The type checker reads the output of cgo in the build cache. Its `//line` directives point back to the file of the repo. So the extractor takes the path, the lines and the source from that file. cgo rewrites a call into C with a pointer on the same line. So the columns after it do not point into that file. The extractor parses the file of the repo again. It pairs each function and each call with the one that the type checker read. It pairs each call by its place in the order of the calls of its function. First a call into C, such as `C.int(1)` or `C.malloc(1)`, drops out of the file of the repo. A call that cgo writes drops out of its output, such as `_Ctype_int(1)` or the check of a pointer. cgo moves a part of a checked argument in front of it, such as `a` of `&a[i]`. The order puts that part back where the argument names it. If the 2 orders hold a different number of calls, no call of that function pairs. Then each call of that function in the file of the repo is an open end with `other`, at its line in that file. A call into C stays a library call. So every unproved call is marked, as story 20 asks. A caller in another load finds the function by the file of the repo, because export data names that file. A call into C is a library call. A call that cgo adds is not in the document.
- **A module that the go tool refuses does not stop the extractor.** An example is a module that needs a newer go under `GOTOOLCHAIN=local`. Its files stay out of the document, and the other modules load. If the go tool refuses the go.work, each module loads on its own.
- **The extractor loads the packages of the files in scope, not each whole module.** So `--scope 'services/billing/**'` type-checks only those packages. The extractor does not load a type of a package that no package in scope imports. So that type implements no interface.
- **The extractor removes `-trimpath` from `GOFLAGS`, as it removes `-mod`.** A `replace` can load a module from the repo. With `-trimpath`, the export data of that module names its files without the path of the repo. Then a call into that module becomes a library call. The extractor reads `GOFLAGS` as the go tool does, from the environment or from the go env file of `go env -w`. It always passes the filtered value, also to the build of the extractor.
- **The test variants load only when a test file is in scope.** So `--scope '!**/*_test.go'` type-checks each package once.

## Why

- **A library interface is not a one-of group, and an interface that only the library implements acts like one.** On gitea, `db.Engine` has no implementation in gitea, and the xorm module implements it. Each call on it was an open end with `no-implementation`, although the code that runs is in a library. The resolution rate does not count a library call, as it does not count a call on `io.Writer`.
- **The name of a parameter is not part of a Go type.** `types.Identical` ignores the names too, but it compares the 2 copies of a named type as different types.
- **Story 29 asks for each Go file in scope in the document.** A module that the `go.work` does not use dropped out of the document with no note. Story 30 still holds for the modules on the use lines.
- **The spec puts in a one-of group the method of each type in scope.** A method that a library type declares is library code, so it stays out, as any other library callee does.
- **A generic type has no type arguments at the call site.** A type argument for each type parameter is the narrowest test that keeps `Box[T]` in the group and `Label[T]` out of it.

## Consequences

- The gitea record of `docs/research/2026-10-26-go-resolution-on-gitea/` counts the calls on `db.Engine`, `db.Session` and `db.EngineMigration` as library calls.
- On 2026-10-27, the base cache keys a Go entry on the dependency files of Go, not on its lock files. ADR-0025 decision 4 says "the lock files". The dependency files of Go are each `go.sum`, each `go.work.sum` and the workspace file `go.work` at the repo root. A `go.work` decides which modules the base loads, as a lock file decides the versions.
