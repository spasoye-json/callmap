Archmap, 2026-10-18

Code to map, with no model

Yes, the technique exists, and it needs no agent. The TypeScript type checker ties each call in a file to the one function that it runs. On a private app it tied 96.7% of backend calls and 98.8% of mobile calls to a function in your own code. The map that it gives is the same for the same code, and it costs no tokens.

What you lose: the business words. A box shows if (!store), not "The store does not exist".

1. The technique: three passes over the code

  1. Parse. ts.createProgram reads every file in the tsconfig.json and builds a syntax tree. The tree knows that line 109 is an if and line 110 is a throw. It does not know what this.ordersService is.
  2. Resolve. checker.getResolvedSignature(call) follows the types. this.ordersService.create(...) has the type OrdersService, because NestJS injects it through the constructor. So the checker returns OrdersService.create in orders.service.ts:97. That is the edge, proven by the compiler.
  3. Control flow. A walk over each function body turns if, switch, throw, try and an early return into decisions and error exits. This is the flowchart inside one function.

Why the type checker and not text search: a text search for "create(" finds 10 methods with that name in the backend. The checker finds the one that runs. Your question "which variables it is calling" is the same pass: checker.getSymbolAtLocation(name) gives the declaration of each variable.

2. The measurement on a private app

Source: a private app, scope server/src and mobile-app, test files left out. The folder names are invented. Script: docs/research/2026-10-18-call-resolution/calls.cjs.

The 13 backend misses are of two kinds:

  • Untyped libraries, 11 calls: bcrypt.hash, bcrypt.compare, sharp and multer. These are leaves anyway. A type package for each library fixes them.
  • A map of strategies, 2 calls: this.rules[kind].bodyOf in export-targets.service.ts:128. These names are invented. The checker knows the interface but not which object runs. The map can draw an edge to each implementation and mark the choice.

3. One real flow, drawn with no model

This is "place an order", from the mobile store to the confirmation mail. Each box is a real line of code. Each label is the code itself.

Source: a private app. The paths and the names in this diagram are invented, because the app is private: mobile-app/stores/order.ts:286, server/src/modules/orders/orders.controller.ts:47, server/src/modules/orders/orders.service.ts:97, server/src/modules/notifications/listeners/mail.listener.ts:44. I drew this diagram by hand from the code. No tool produced it yet.

How each arrow is found, with no model:

  1. Mobile to backend: the call POST("/orders") has a string. The controller has @Controller('orders') and @Post(). A rule joins the two strings and matches them. A route that the code builds at run time does not match, and the map shows it as an open end.
  2. Controller to service: the type checker resolves this.ordersService.create to orders.service.ts:97. This is a proof.
  3. Inside the service: the walk over the function body gives the order of the steps, the 3 decisions and the 2 error exits. This is a proof too.
  4. Side effects: a short rule list marks the calls that change state: a TypeORM save, update or delete, an emit, and an HTTP call.
  5. Service to listener: emit and @OnEvent use the same constant, OrderEvents.OrderPlaced. The checker proves that it is the same symbol, so this match is stronger than a string match.

4. What the view without a model cannot do

  • Business words: the boxes show code. If your names are good, the code reads well. !product is clear. A name like handle2 is not.
  • Which branch matters: every if becomes a decision, also a small one. A long function gives a tall chart. Collapse per function helps.
  • Dynamic calls: an any value, a callback, or a route built at run time. The measurement shows that these are few in the private app.

A model can come later, for the words only. It reads the drawn flow and writes one plain label per box. It never adds or removes a box or an arrow. A content hash keeps each label until the code under it changes.

5. What this changes in the Archmap plan

  • The flow comes from code, not from a trace pass. The trace pass, the curation by Claude, and the AI discovery pass leave the first version.
  • Accuracy is a number: the share of calls that the checker resolved. You can show it for each flow.
  • The same code gives the same map, with no hash rule needed for the structure. The compiler is deterministic.
  • The review is a diff of two graphs: the graph on the merge base and the graph on the branch. Code computes it in seconds, with no tokens.
